The harness is fundamentally sound: the differential oracle is string-free, the
sandbox is thoughtfully constructed (the `urllib` egress note shows real rigor), the
scope guard is a genuine single chokepoint, and the web console's auth uses PBKDF2 +
HMAC-signed sessions with login lockout. The issues below are the gaps that matter at
enterprise grade, plus one functional bug that made the **reasoner model unusable**.

---

## 1. HIGH — Redirect-following bypassed the scope guard

**Where:** `venom/engine/http_client.py`

**What:** `ScopedClient.request()` called `scope.assert_request_allowed()` only for the
*initial* URL, then handed `follow_redirects=True` to httpx. httpx follows 30x
redirects **internally**, so a target that responds `302 Location: https://evil.example/…`
would have that off-scope request sent with **no scope check** — leaking the
`X-Pentest-ID` header and any auth headers/cookies off the authorized surface. This
directly contradicts the module's own invariant: *"there is no code path to the
network that bypasses the scope check."*

**Fix:** Registered an httpx **request event hook** (`_guard_request`) that re-runs the
scope guard on *every* emitted request, including each redirect hop — **before** it
leaves the process (prevention, not detection). Added `count_destructive=False` to
`Scope.assert_request_allowed()` so per-hop re-validation enforces permission +
membership without double-charging the destructive budget.

**Proof:** `tests/test_scope_redirect_guard.py` — out-of-scope redirect is blocked and
the evil host is never contacted; in-scope relative redirects still work; a single
DELETE that 307-redirects consumes exactly one budget slot.

## 2. FUNCTIONAL (LLM) — Reasoner model silently unusable on DeepSeek

**Where:** `venom/agents/roles.py :: AgentSpec.model()`

**What:** `model()` ran the configured model name through `resolve_nvidia_model()`
**regardless of provider**. `deepseek-v4-pro` (the reasoner) is a **key** in the NVIDIA
alias catalog, so it was rewritten to `deepseek-ai/deepseek-v4-pro` and sent to
**DeepSeek's** OpenAI-compatible API, which rejects it with **HTTP 400**. The router
then silently fell back NVIDIA → OpenRouter → **Ollama**, so a run nominally "on the
reasoner" was actually answered by the local model. The roles.py comment claimed the
alias map was "a harmless pass-through for non-NVIDIA providers" — it was not.

This was found by the live validation: `VENOM_MODEL_CODEGEN=deepseek-v4-pro` produced
a wall of `400 Bad Request` then Ollama answers. The model itself accepts the exact
payload fine (verified directly), proving the bug was the name rewrite.

**Fix:** Made resolution **provider-aware** — the NVIDIA catalog is consulted only when
`spec.provider == NVIDIA_NIM`; DeepSeek/OpenRouter/Ollama pass the configured name
through unchanged.

**Proof:** `tests/test_agent_model_resolution.py` (+ updated `tests/test_agents.py`).

## 3. MEDIUM — Web login leaked account existence via timing

**Where:** `venom/web/auth.py :: authenticate()`

**What:** When the username didn't exist, `verify_password` (200k-round PBKDF2) was
never called, so "no such user" returned measurably faster than "wrong password" —
a classic **user-enumeration** side channel on a console that can launch authenticated
attacks.

**Fix:** Always run a constant-cost PBKDF2 verification (against the real hash, or a
module-level `_DUMMY_HASH` of equal cost) so the two cases are timing-indistinguishable.

**Proof:** `tests/test_security_hardening.py::test_authenticate_unknown_user_still_runs_password_verify`.

---

## 4. MEDIUM — Secrets could survive into the signed audit trail

**Where:** `venom/tools/base.py :: Toolbox.audit()`

**What:** Audit paths were scrubbed only with PII-`redact()`, which is intentionally
**disengaged** when the operator sets `allow_pii_capture=true`. A provider API key /
bearer token embedded in a URL could then land in the HMAC-signed, persisted trail —
despite the always-on secret-redaction promise.

**Fix:** Apply the always-on `redact_secrets()` in addition to `redact()`, so provider
keys/bearer tokens are stripped from the audit trail regardless of the PII setting.

**Proof:** `tests/test_security_hardening.py` (two cases, PII capture on and off).

---

## 5. MEDIUM — `.env.template` shipped a weak console password

**Where:** `.env.template`

**What:** `auth.py` deliberately removed the old weak `admin/venom` default ("this
console can launch authenticated attacks, so it must never ship with guessable
credentials"). But the template re-introduced exactly that with
`VENOM_WEB_PASSWORD=venom`, so anyone copying it got the weak password back.

**Fix:** Commented the variable out with guidance to leave it unset (→ strong random
one-time password printed at first start), and to never ship a guessable value.

## 6. LOW — Sandbox hardening (defense-in-depth) + frontend/quality fixes

- **Sandbox frame-walk attributes** (`venom/tools/base.py`): the AST validator blocked
  dunder attributes (`startswith("__")`) but not the non-dunder rungs of a frame-walk
  (`gi_frame`, `cr_frame`, `tb_frame`, `f_back`, `f_globals`, `f_builtins`, …). Full
  escape was **not** reachable today (no way to obtain an out-of-sandbox frame), but the
  guarantee shouldn't rely on that. Added a denylist; `tests/test_exploit_sandbox.py::
  test_frame_walking_attributes_rejected` proves rejection without false positives.
- **Top-bar target label** (`venom/web/ui/app.jsx`): hardcoded `localhost:8000 · VulnLab`
  even for external-target runs. Now derived from the selected engagement.
- **Status-pill consistency** (`venom/web/ui/app.jsx`): the top-bar pill showed
  "engagement complete" on the Findings/Report routes even while the run was still
  live (it keyed off the route, not the run state). Now reflects `runFinished`.
- **Stale provider comment + default** (`venom/llm/providers.py`): the fallback-chain
  comment said "NVIDIA NIM leads" while the chain leads with DeepSeek; the no-route
  default also pointed at NVIDIA. Both corrected to DeepSeek (the configured primary).

## 7. Live validation (DeepSeek V4, on the purchased API)

Server-less, in-process against the bundled VulnLab (`vulnlab_coverage`), the
autonomous `oneshot` hunt (per-lab budget 4) on a 10-lab representative subset:

| Model (CodeGen role) | Solved | Labs proven | Wall-clock |
|---|---|---|---|
| `deepseek-v4-flash` (fast; `deepseek-chat`) | **6 / 10** | bola, coupon, idor, jwt, trustid, workflow | 101s |
| `deepseek-v4-pro` (reasoner) | **5 / 10** | bola, idor, jwt, money, trustid | 654s* |

\* the reasoner run overlapped a live console engagement, so its wall-clock was
inflated by shared DeepSeek RPM throttling; the solve count stands.

**Honest reading:** the reasoner was *not* uniformly stronger on this set — it
uniquely solved the hard `money` (infinite-money) lab but missed `coupon`/`workflow`;
both models missed `price`/`mass`/`io`. Four labs are solved by both (idor, jwt,
trustid, bola), so the harness + oracle are clearly exercising real exploitation, not
luck. **The functional reasoner result was only obtainable after fixing §2** — before
that, `deepseek-v4-pro` 400'd and silently ran on Ollama.

A full web-console engagement against the **combined 37-lab surface** (recon → infer →
hypothesize → exploit → verify, then per-lab coverage) confirmed **17 HIGH findings
across 47 test cases, 107 endpoints discovered** — rendered live in the console
(dashboard → live trace → findings → report, all screenshotted in the README).

## Verified-clean (audited, no change needed)

- **Differential oracle** (`cognition/objective.py`): `_DEFAULT_SIGNALS` is empty;
  no baked-in lab strings; honest `False` when neither win-action nor marker is set.
- **Frontend XSS**: the only two `dangerouslySetInnerHTML` sinks render
  `highlightPy(code)`, which HTML-escapes `&<>` **before** tokenizing — injection-safe.
  Every other field uses React's auto-escaping. LLM/target-derived content cannot
  inject markup.
- **Static file serving** (`web/server.py`): path-traversal-safe (`is_relative_to`),
  with `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`.
- **Run authorization**: ownership persists (engagements.json + trace.json), so per-run
  visibility survives a restart (no cross-operator read).
- **Audit HMAC** (`audit.py`): SHA-256, `compare_digest`, default-key honesty flag.

## Residual notes (documented, not bugs)

- The sandbox is, by design, *defense-in-depth, not a hard sandbox* — run fully
  untrusted models in a container (already stated in CLAUDE.md §9). A runtime-built
  `str.format` template can still reach object reprs (info-only; no calls possible via
  the format mini-language).
- UI libs (React/Babel) load from unpkg CDN without SRI integrity hashes and use dev
  builds + in-browser Babel — fine for a localhost console, but vendoring + precompiled
  JSX + SRI is recommended before any non-local deployment (tracked as follow-up).
- The web launcher accepts any external `target_url` from an authenticated operator and
  defaults `authorized_by` if blank; the wizard requires it, but the API does not. An
  enterprise deployment should enforce non-empty authorization server-side for
  non-bundled targets.
